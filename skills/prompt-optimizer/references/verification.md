# 验证协议

没有跑过对比的优化，只是换了个写法。这一节定义什么叫"跑过"。

## 一、评测集

样本量按故障类型分层，不要按"看起来有代表性"抽。

| 层 | 数量 | 用途 |
|---|---|---|
| 每个失败类型 | ≥5 条 | 主指标，证明优化有效 |
| 边界与对抗 | 3–5 条 | 空输入、超长输入、纯英文、注入式指令（"忽略以上规则"） |
| 过去一直正常的 | 5–10 条 | 回归护栏，防止修好 A 弄坏 B |

总数 20–40 条就够做方向性判断。几百条是上线评审的规模，不是判断改法是否有效的规模。

每条样本存三样：输入、期望输出的**判定方式**、分层标签。期望值优先写成可编程断言（正则、JSON schema、字段校验、长度区间），不能断言的（如"语气是否得体"）单列人工评审。

## 二、跑法

### A. 代码内（Spring AI / 任意 SDK）

同一批样本，分别用旧 prompt 和新 prompt 跑 K 次，落盘结果，再用断言打分。要点：

- 每样本 K ≥ 5，记录通过率而不是单次结果。
- 温度、`maxTokens`、模型版本在两版之间保持完全一致，否则测的是参数不是 prompt。
- 用结构化输出时，解析失败也要算进分母，不要静默丢弃 —— 那是优化最想知道的数字。

```java
record Case(String id, String layer, String input, Predicate<Outcome> expect) {}

// 同一 Case 列表、同一 ChatOptions，只换 SystemMessage
for (Case c : cases) {
    for (int k = 0; k < 5; k++) {
        Outcome out = run(PROMPT_V2, c.input());   // 解析失败 -> Outcome.parseError
        results.add(new Result(c.id(), c.layer(), out, c.expect().test(out)));
    }
}
// 输出：分层通过率、解析失败率、超长率、回归层通过率
```

### B. 只有 DSH

用 subagent 当采样器：同一个任务、同一批输入，对每个变体重复派发 5 次以上，收集原始输出后人工比对。

- 派发时不要提"这是评测"或"请表现好一点"，那会污染样本。
- 变体之间用相同的会话设定、相同的模型，只换被评测的提示词。
- 让子 agent 原样返回输出，不要让它自己评价好坏 —— 自评会把偏好当成事实。

这种方式给的是方向性证据，不是统计结论。交付时如实标注样本量和局限。

## 三、评分表

每个变体填一张，数字必须来自实际运行：

| 指标 | 定义 | 旧 | 新 | 变化 |
|---|---|---|---|---|
| 格式合法率 | 可被解析且类型正确的比例 | | | |
| 目标指标 | 本次要修的那个故障（如 summary ≤50 字） | | | |
| 边界通过率 | 对抗样本层的通过率 | | | |
| 回归通过率 | 原本正常样本层的通过率 | | | |
| 解析失败数 | 结构化输出的异常条数 | | | |
| prompt 规模 | 字符数 / token 数 | | | |
| 单次成本 | 输入 token × 单价 + 平均输出 token × 单价 | | | |
| 平均延迟 | 端到端耗时 | | | |

## 四、判定

**变好了**要同时满足：

1. 目标指标上升，且上升幅度超过同变体内 K 次的波动范围。
2. 回归层没有下降。
3. 记账部分的变化被接受（token 涨了 60% 换 3 个点是不是划算，由用户决定，不由你决定）。

不满足任何一条，就写"有效果但不满足条件"或"未见效果"，附数字。

## 五、自欺清单

- **单样本定论。** 一次通过不等于稳定，五次里三次通过才是信息。
- **自动计数当结论。** 模板回显、反面示例、被截断的输出都会伪装成命中，命中的每条都要人读。
- **只测想测的。** 格式合法率上去了、回答可用性掉了，是这类任务最常见的回归。
- **悄悄换参数。** 顺手把 temperature 从 0.7 改成 0、把模型换成更强的，数字当然好看，但那不是 prompt 的功劳。
- **合成样本当真实流量。** 合成样本只覆盖你想得到的失败。
- **用"通常""预计""应该"替代数字。** 出现这类词即视为未验证。
